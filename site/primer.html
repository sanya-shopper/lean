What Lean actually is

Two tools in one coat, unified by a single idea.

Lean 4 is a dependently-typed functional programming language and an interactive theorem prover — the same language for both. The link is the Curry–Howard correspondence: a proposition is a type, a proof is a term (a program) of that type, and so type-checking is proof-checking. A wrong proof is simply a term that fails to type-check.

What you trust is a small, audited kernel that only verifies terms against their types. Every tactic, every piece of automation — however elaborate or buggy — must ultimately emit a term the kernel re-checks. That is why you can lean on powerful automation without risking soundness.

Situating it: vs. TLA+ and Haskell

You likely know one of these. The differences tell you exactly which questions Lean is for.

AxisTLA+Lean 4Haskell
Primary job Specify systems & temporal behavior Prove theorems; write verified programs Write programs
How you check Model-check a finite state space (TLC); finds counterexamples Deduce over possibly-infinite objects; no counterexamples unless you search Type-check; run tests
Scope of a claim Bounded, automatic, exhaustive-within-bounds Unbounded (∀), manual + tactic-assisted Types constrain; no proofs of behavior
Types Untyped set theory Full dependent types — types depend on values, can express theorems Hindley–Milner + extensions; no value-dependent types
Totality n/a Total by default (termination-checked) — so a function can be a proof Lazy & partial; ⊥ inhabits every type
Reach for it when… "Does my concurrent design have a bad interleaving?" "Is this true for all inputs, provably?" "Can I write this elegantly?"

Lean has #eval and decide/native_decide for bounded, computational checks — which can feel a little model-checker-ish on finite decidable props — but that is evaluating a decision procedure, not exploring a temporal state space.

The proof experience

Term mode, tactic mode, and the tactics you'll actually use.

A proof is either a term you hand Lean directly, or — more often — a sequence of tactics in a by block that transform the goal while Lean assembles the term behind the scenes. In an editor, the infoview shows the live goal state (your hypotheses and what remains) after every tactic.

Primer/Proofs.lean — all of these type-check
-- proof by computation: both sides reduce to the same value
theorem two_plus_two : 2 + 2 = 4 := by rfl

-- a decidable fact, settled by actually evaluating it
example : (7 * 6 = 42) ∧ (3 < 10) := by decide

-- linear arithmetic: omega closes goals rfl/decide can't
example (a b : Nat) : a + b = b + a := by omega

-- a ∀-statement proved by induction (length is preserved by map)
theorem length_map (f : α → β) (xs : List α) :
    (xs.map f).length = xs.length := by
  induction xs with
  | nil => rfl
  | cons x xs ih => simp [List.map, List.length, ih]

sorry is a hole — a placeholder that admits any goal so you can sketch a proof's shape and fill gaps later. Lean warns loudly while one remains, because the proof isn't actually done.

The crypto-relevant layer: BitVec

Fixed-width machine words — exactly what SHA-256 is built from — and where brute force stops and SAT begins.

BitVec 32 gives you 32-bit words with wraparound arithmetic: modular add, XOR/AND/NOT, rotation and shift. SHA-256's whole primitive layer is a few lines, and it's a natural bridge from this primer into the formalization survey.

Primer/BitVec.lean — SHA-256's building blocks, verbatim
def rotr (x : BitVec 32) (n : Nat) : BitVec 32 :=
  (x >>> n) ||| (x <<< (32 - n))

def Ch     (x y z : BitVec 32) := (x &&& y) ^^^ ((~~~x) &&& z)
def Maj    (x y z : BitVec 32) := (x &&& y) ^^^ (x &&& z) ^^^ (y &&& z)
def Sigma0 (x : BitVec 32) := rotr x 2 ^^^ rotr x 13 ^^^ rotr x 22

-- ALL 256 eight-bit words: decide can brute-force this
example : ∀ x : BitVec 8, x ^^^ x = 0#8 := by decide

-- the SAME over 32 bits is 2^32 cases — decide is hopeless.
-- import Std.Tactic.BVDecide, then this solves instantly:
--   example (x : BitVec 32) : x ^^^ x = 0#32 := by bv_decide
-- (bitblast to SAT + check an LRAT certificate — no enumeration)
Why this matters for the survey. bv_decide — verified bitblasting with a Lean-checked LRAT certificate — is the reason Lean is now a strong platform for bit-level crypto proofs, even though it hasn't yet produced a software SHA-256 correctness proof.

Verifying properties of your own projects

What Lean can and can't do for your code — set expectations correctly.

Lean is excellent for proving properties of pure functions, data-structure invariants, and math-heavy kernels that you model or re-implement in Lean. It is not a push-button verifier for an arbitrary existing Rust/Python/C repo — that's the domain of SMT-backed tools (Dafny, Why3) or model checkers (TLA+). The productive loop:

  1. Model the pure core of your algorithm as Lean functions (or re-implement it directly).
  2. State the properties you care about as theorems.
  3. Prove them — automation first (simp / omega / decide), hand-guiding only the rest. #eval gives a fast spot-check loop while you work.
Primer/Spec.lean — a fast implementation proved equal to a reference model
def sumTo : Nat → Nat                -- reference model
  | 0     => 0
  | n + 1 => (n + 1) + sumTo n

def sumToAcc : Nat → Nat → Nat       -- "optimized" tail-recursive version
  | 0,     acc => acc
  | n + 1, acc => sumToAcc n (acc + (n + 1))

theorem sumTo_correct (n : Nat) : sumToAcc n 0 = sumTo n := by
  simp [sumToAcc_eq]              -- via a generalized accumulator lemma

Cookbook & running it

Copy-paste recipes, then the two commands that check everything.

Evaluate an expression
#eval (List.range 10).map (· * 2)
Check a type without running
#check List.map
Prove by computation
example : 2 + 2 = 4 := by rfl
Prove a decidable fact
example : 7 * 6 = 42 := by decide
Linear arithmetic
example (a b : Nat) : a + b = b + a := by omega

Build = verification

There is no separate test step: a clean build is the proof that every theorem goes through.

# type-check ALL chapters (= check all proofs)
lake build

# run one chapter, printing its #eval / #check output
lake env lean Primer/Basics.lean
Biggest ergonomic upgrade: open the project in VS Code with the Lean 4 extension. The live infoview — the goal state updating as you move your cursor through a proof — is the single largest jump over the command line.
