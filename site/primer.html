What Lean actually is

Two tools in one coat, unified by a single idea.

Lean 4 is a dependently-typed functional programming language and an interactive theorem prover — the same language for both.

The functional-programming half looks like any ML/Haskell descendant — definitions, pattern matching, recursion, algebraic data types:

Primer/Basics.lean
def double (n : Nat) : Nat := n + n        -- a function Nat → Nat

def fib : Nat → Nat                       -- recursion + pattern matching
  | 0 => 0
  | 1 => 1
  | n + 2 => fib n + fib (n + 1)

#eval fib 10                             -- 55  (#eval runs the code)

The dependently-typed half is the part with no Haskell analogue: a type may mention a value. A vector's length lives in its type, so the type-checker — not a runtime check — enforces the sizes:

-- `Vector α n` is a list of α whose length n is part of the type.
example : Vector Nat 3 := #v[10, 20, 30]     -- ok
-- example : Vector Nat 3 := #v[10, 20]      -- TYPE ERROR: length 2 ≠ 3

-- append's type PROMISES the output length is the sum of the inputs':
#check (Vector.append : Vector α m → Vector α n → Vector α (m + n))

Because a type can depend on values, a type can also encode a mathematical statement — and that is exactly the bridge to the theorem-prover half.

What "theorem prover" means, concretely

Proving = building a term; checking = type-checking that term.

By Curry–Howard a proposition is a type and a proof is a term of that type. So proving P means constructing a value whose type is P, and checking a proof is the same thing a compiler already does — verifying a term has the type it claims.

An aside on rfl, which you'll see everywhere: it is the one canonical proof that a thing equals itself — its type says a = a holds for every a. It closes a goal x = y exactly when x and y compute to the same value (so 2 + 2 = 4 is closed by rfl, since 2 + 2 reduces to 4) — but a + b = b + a is not, since the sides don't reduce to a common form (there you use omega).

Something less trivial than 2 + 2: the sum of the first n odd numbers is n², proved by a genuine induction with a real algebraic step.

Primer/Proofs.lean — this type-checks
def sumOdd : Nat → Nat
  | 0 => 0
  | n + 1 => sumOdd n + (2 * n + 1)    -- add the (n+1)-th odd number

theorem sumOdd_eq (n : Nat) : sumOdd n = n * n := by
  induction n with
  | zero => rfl                        -- base: 0 = 0*0, by computation
  | succ k ih =>
      have h : (k+1)*(k+1) = k*k + 2*k + 1 := by
        simp only [Nat.succ_mul, Nat.mul_succ]; omega
      simp only [sumOdd, ih, h]        -- uses the induction hypothesis ih
      omega

What does the system actually output as "the proof"? A by … block is only sugar: it elaborates to an ordinary term, and it is that term the kernel checks. You can print it — and the trivial one is exactly what you'd guess (the tactic rfl built the term Eq.refl (2 + 2)):

what Lean generates — #print
#print two_plus_two
-- theorem two_plus_two : 2 + 2 = 4 :=
-- Eq.refl (2 + 2)

#print sumOdd_eq        -- the induction became Nat's recursor:
-- theorem sumOdd_eq : ∀ (n : Nat), sumOdd n = n * n :=
-- fun n => Nat.recAux (Eq.refl (sumOdd 0))   -- the `zero` case
--            (fun k ih => …)                 -- the `succ` case, using ih
--            n

You never write that term by hand — that's the point of tactics. But it exists, and a small, fixed kernel (a few thousand lines) re-checks it. Tactics live outside the kernel, so a buggy tactic can't produce a false theorem — whatever it emits must still pass the kernel. The trusted base is the kernel alone. A proof can also contain sorry, an explicit hole you fill later; Lean warns while any remains.

Situating it: vs. TLA+ and Haskell

You likely know one of these. The differences tell you exactly which questions Lean is for.

AxisTLA+Lean 4Haskell
Primary job Specify systems & temporal behavior Prove theorems; write verified programs Write programs
How you check Model-check a finite state space (TLC); finds counterexamples Deduce over possibly-infinite objects; no counterexamples unless you search Type-check; run tests
Scope of a claim Bounded, automatic, exhaustive-within-bounds Unbounded (∀), manual + tactic-assisted Types constrain; no proofs of behavior
Types Untyped set theory Full dependent types — types depend on values, can express theorems Hindley–Milner + extensions; no value-dependent types
Totality n/a Total by default (termination-checked) — so a function can be a proof Lazy & partial; ⊥ inhabits every type
Reach for it when… "Does my concurrent design have a bad interleaving?" "Is this true for all inputs, provably?" "Can I write this elegantly?"

Lean has #eval and decide/native_decide for bounded, computational checks — which can feel a little model-checker-ish on finite decidable props — but that is evaluating a decision procedure, not exploring a temporal state space.

Is Lean general-purpose? IO, data, and C

Yes — and it goes both ways across the C boundary.

Lean 4 is a genuine general-purpose language, not a proof-only toy. It compiles to C then native code, has an IO monad for real input/output, ships arrays, hash maps, strings and ByteArray for data manipulation, and is substantial enough that the Lean compiler and much of its standard library are written in Lean itself. So it is suitable for library-building and data/IO tools.

a real program, and both directions of C interop
def main : IO Unit := do
  let line ← (← IO.getStdin).getLine
  IO.println s!"you said: {line.trim}"   -- string interpolation

-- Call C FROM Lean: bind a Lean decl to an external C symbol.
@[extern "lean_sqrt"] opaque cSqrt (x : Float) : Float

-- Call Lean FROM C: export under a C-callable name (link libleanshared).
@[export my_add] def myAdd (a b : Nat) : Nat := a + b

Both directions work: @[extern] calls C from Lean; @[export] makes a Lean function C-callable. The one caveat is the runtime: compiled Lean is C plus the Lean runtime and its reference-counted object model (lean_object*), so embedding Lean links a runtime rather than dropping in a freestanding .o. It is not a no-runtime systems language.

Editors — and Xcode

Lean ships a language server (lean --server, speaking LSP), so any LSP client works. The most complete first-party integration is the VS Code extension; the mainstream non-VS-Code choices are Emacs (lean4-mode) and Neovim (lean.nvim), both with live infoview. There is no Lean plugin for Xcode — Xcode exposes no third-party-language/LSP extension point, and none exists as of 2026. Staying in the Apple toolchain means the command line (below) plus an LSP editor like Emacs or Neovim alongside it. Command-line only is fully viable — and how this project is checked.

The proof experience

Term mode, tactic mode, and the tactics you'll actually use.

A proof is either a term you hand Lean directly, or — more often — a sequence of tactics in a by block that transform the goal while Lean assembles the term behind the scenes. In an editor, the infoview shows the live goal state (your hypotheses and what remains) after every tactic.

Primer/Proofs.lean — all of these type-check
-- proof by computation: both sides reduce to the same value
theorem two_plus_two : 2 + 2 = 4 := by rfl

-- a decidable fact, settled by actually evaluating it
example : (7 * 6 = 42) ∧ (3 < 10) := by decide

-- linear arithmetic: omega closes goals rfl/decide can't
example (a b : Nat) : a + b = b + a := by omega

-- a ∀-statement proved by induction (length is preserved by map)
theorem length_map (f : α → β) (xs : List α) :
    (xs.map f).length = xs.length := by
  induction xs with
  | nil => rfl
  | cons x xs ih => simp [List.map, List.length, ih]

sorry is a hole — a placeholder that admits any goal so you can sketch a proof's shape and fill gaps later. Lean warns loudly while one remains, because the proof isn't actually done.

The crypto-relevant layer: BitVec

Fixed-width machine words — exactly what SHA-256 is built from — and where brute force stops and SAT begins.

BitVec 32 gives you 32-bit words with wraparound arithmetic: modular add, XOR/AND/NOT, rotation and shift. SHA-256's whole primitive layer is a few lines, and it's a natural bridge from this primer into the formalization survey.

Primer/BitVec.lean — SHA-256's building blocks, verbatim
def rotr (x : BitVec 32) (n : Nat) : BitVec 32 :=
  (x >>> n) ||| (x <<< (32 - n))

def Ch     (x y z : BitVec 32) := (x &&& y) ^^^ ((~~~x) &&& z)
def Maj    (x y z : BitVec 32) := (x &&& y) ^^^ (x &&& z) ^^^ (y &&& z)
def Sigma0 (x : BitVec 32) := rotr x 2 ^^^ rotr x 13 ^^^ rotr x 22

-- ALL 256 eight-bit words: decide can brute-force this
example : ∀ x : BitVec 8, x ^^^ x = 0#8 := by decide

-- the SAME over 32 bits is 2^32 cases — decide is hopeless.
-- import Std.Tactic.BVDecide, then this solves instantly:
--   example (x : BitVec 32) : x ^^^ x = 0#32 := by bv_decide
-- (bitblast to SAT + check an LRAT certificate — no enumeration)
Why this matters for the survey. bv_decide — verified bitblasting with a Lean-checked LRAT certificate — is the reason Lean is now a strong platform for bit-level crypto proofs, even though it hasn't yet produced a software SHA-256 correctness proof.

Verifying properties of your own projects

What Lean can and can't do for your code — set expectations correctly.

Lean is excellent for proving properties of pure functions, data-structure invariants, and math-heavy kernels that you model or re-implement in Lean. It is not a push-button verifier for an arbitrary existing Rust/Python/C repo — that's the domain of SMT-backed tools (Dafny, Why3) or model checkers (TLA+). The productive loop:

  1. Model the pure core of your algorithm as Lean functions (or re-implement it directly).
  2. State the properties you care about as theorems.
  3. Prove them — automation first (simp / omega / decide), hand-guiding only the rest. #eval gives a fast spot-check loop while you work.
Primer/Spec.lean — a fast implementation proved equal to a reference model
def sumTo : Nat → Nat                -- reference model
  | 0     => 0
  | n + 1 => (n + 1) + sumTo n

def sumToAcc : Nat → Nat → Nat       -- "optimized" tail-recursive version
  | 0,     acc => acc
  | n + 1, acc => sumToAcc n (acc + (n + 1))

theorem sumTo_correct (n : Nat) : sumToAcc n 0 = sumTo n := by
  simp [sumToAcc_eq]              -- via a generalized accumulator lemma

Cookbook & running it

Copy-paste recipes, then the two commands that check everything.

Want to run these without installing anything? Paste them into the official Lean web playground — it runs Lean in the browser with a live infoview.

Build = verification

There is no separate test step: a clean build is the proof that every theorem goes through.

# type-check ALL chapters (= check all proofs)
lake build

# run one chapter, printing its #eval / #check output
lake env lean Primer/Basics.lean
The infoview is the big ergonomic win. Lean's language server (lean --server, LSP) drives a live infoview showing the goal state as your cursor moves through a proof. Get it in Emacs (lean4-mode) or Neovim (lean.nvim) — there is no Xcode plugin — or skip the editor entirely and work from the command line as this project does.
