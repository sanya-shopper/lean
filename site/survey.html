Formalizing SHA-256 analysis in Lean: where the map ends

The proof-assistant world has thoroughly verified that SHA-256 implementations compute the spec and that constructions built on it are secure under assumptions. It has never formally reasoned about attacking or analyzing the primitive. That gap — plus Lean's own catch-up debt — is the contribution boundary.

scope · Lean 4 / mathlib + adjacent ITPs threads · SHA-2 impl · differential cryptanalysis · SAT/SMT · verified-crypto method · web + repo inspection + local Lean experiments

The three facts that frame everything

Read these before the detail. Each is the answer to a question people assume is already solved.

0
cryptographic hash functions in mathlib, Lean core, or Batteries — and no abstract "hash function" definition. Confirmed by code search.
circuit only
Lean's strongest verified SHA-256 is a ZK-circuit compression gadget (clean). No Lean proof of a software SHA-256 vs FIPS spec — the Coq/VST result from 2015 has no Lean twin.
never
Differential cryptanalysis has not been formalized in any proof assistant — no machine-checked differential probability, characteristics, or attack bounds anywhere.

The boundary, drawn

Two activities get conflated in "verifying SHA-256." One territory is densely settled across five ecosystems; the other is empty ground.

Settled territory

Implementation correctness & provable security

HACL* / F* Coq · VST SHA-256 SAW · Cryptol Jasmin · EasyCrypt CryptHOL Lean · LNSym (SHA-512) Lean · clean (SHA-256 circuit)
the boundary
Open frontier

Cryptanalysis & analysis of the primitive

differential probability — unformalized characteristics / trails — unformalized collision-attack theory — unformalized verified collision certificate — none

Every settled-side result treats the intrinsic strength of SHA-256 — collision and preimage resistance — as an unproven assumption or an idealization. Nobody has crossed to "does this concrete attack work, and with what probability?"

Four threads, briefly

What each research pass found. Full detail and citations live in NOTES.md.

01 · SHA-2 in Lean

No hash in mathlib. But the BitVec primitive layer is mature and bv_decide (verified bitblasting, shipped Lean 4.12) dispatches SHA's Ch/Maj/Σ/σ identities instantly. Verified SHA-256 exists only at the circuit level (clean); LNSym proves SHA-512 assembly, not 256.

strong platform, thin results
02 · Differential cryptanalysis

Never formalized in Lean, Coq, Isabelle, or EasyCrypt. The classical theory (Lipmaa–Moriai, De Cannière–Rechberger, Nyberg–Knudsen) is rigorous paper; the search tools (CryptoSMT, AutoDiVer) are unverified. SHAttered had no machine-checked part.

wide open — first-of-its-kind ground
03 · SAT / SMT in Lean

bv_decide fits crypto's bit layer and never trusts the solver (LRAT certificate checked by a Lean-verified checker). But modular-addition-heavy goals blow up — a single SHA-512 lemma produced a 207 MB certificate. Workable pattern: normalize word-algebra first, bitblast only the residue.

capable, with a scaling ceiling
04 · Adjacent verified crypto

HACL*, SAW, VST, CryptHOL, Jasmin all prove code = spec and secure-by-reduction. Verified SHA-2 ships in Firefox, the Linux kernel, and CPython ≥3.12. None of them does cryptanalysis — the boundary is deliberate and industry-wide.

mature, correctness-only

Where a volunteer could contribute

A map, not a commitment — sizing and selection are a later call. Two kinds of opening: catch-up gaps well-trodden elsewhere, and analysis gaps untouched in every proof assistant. Chips encode rough effort and novelty.

A
Lean catch-up gaps
Reproduce known results in Lean. Useful to the ecosystem, lower novelty and risk.
A1 · Canonical Lean SHA-256 spec + core property proofs effort: small–mednovelty: low

Padding injectivity, message-schedule well-formedness, one-block vs multi-block agreement. Several unconnected spec copies exist today — a consistency-drift risk worth closing.

A2 · Optimized SHA-256 ⟷ reference-spec equivalence effort: med–largenovelty: low

The Appel-2015 / HACL* result Lean still lacks for SHA-256: an efficient implementation proved equal to the spec via bv_decide on bit-cores + induction across rounds. Best "ecosystem-useful" pick.

A3 · Merkle–Damgård scaffolding effort: small–mednovelty: low

Length-extension structure and padding lemmas that no Lean project currently has.

B
Analysis / cryptanalysis gaps
Untouched in every proof assistant. Any of these would be a first machine-checked result of its kind.
B1 · Lipmaa–Moriai modular-addition differential probability ◆ top probe effort: smallnovelty: high

Formalize the log-time algorithm for the differential probability of addition mod 2³² (xdp⁺ / adp⊕) with a machine-checked correctness proof against the semantic definition over BitVec 32. Bounded, needs no mathlib, sits exactly where Lean is strongest, follows a clean paper proof — and would be first-of-its-kind. The recommended first bite.

B2 · Verified difference-distribution-table (DDT) theory effort: small–mednovelty: high

Define an S-box's DDT, prove row-sum / differential-uniformity invariants, machine-check a real small S-box. Foundational DC infrastructure (block-cipher-facing, since SHA-256 has no S-box).

B3 · Verified characteristic-probability calculator effort: largenovelty: high

Formalize De Cannière–Rechberger generalized conditions and their propagation, proving computed characteristic probability sound. Effectively a verified core of AutoDiVer/CryptoSMT — or a Lean-checkable certificate such a tool could emit.

B4 · Verified collision / near-collision certificate checker effort: largenovelty: high

Bridge Lean's existing verified LRAT checker to an actual hash differential result — the missing link between "SHAttered gives two files" and a machine-checked "the attack search was sound." Depends on the certificate-size ceiling from thread 03.

If any work is ever scoped, start with B1. It is small enough for one volunteer, needs only BitVec, has a clean correctness proof to follow, and lands on the exact primitive layer where Lean's tooling is strongest — while being a genuine first. A2 is the alternative if the goal is ecosystem-useful rather than research-novel.

Caveat. The "first-ever" claims rest on web search plus abstract/PDF reads — not on cloning and grepping mathlib and the Coq & Isabelle AFP repositories directly. That grep should be done before publishing any "first" claim.
